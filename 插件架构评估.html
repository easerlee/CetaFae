4 边界结论

知识层（软件身份、任务知识、视图选择、阻塞点、启用清单）可插件化；机制层（生命周期、授权、采集、网关、写入、安装、恢复）必须打洞。洞须为宿主通用端口，不向插件交句柄/代码/网络。一致性冲击取决于第一方是否同端口同契约：同权则可保留原则；私有洞则原则失效。需定标为「机制宿主+知识插件」或收紧为「数据包+宿主端口」，分界是洞是否对第三方同权。

5 边界测试失败点

多实例/标题漂移→错绑；UIA树变/视图错→错指；阻塞点漏→错候选；任务ID/版本/语言不配→拒或错任务；未知字段/重解析点→整目录拒（可用性）；快照后文件变→TOCTOU；插件加载成本→3s/90MB破；未验证包宣称支持→范围误导；TC-3写失败→文档损坏；禁用/移除未取消会话→标记残留；日志脱敏漏→泄露；宿主出现软件名分支→原则破。

第三方插件三阶段威胁建模

一、阶段 × 威胁 × 前置条件 × 现状缺口

阶段一（声明式数据包，无代码）

威胁 前置条件 现状缺口
恶意插件窃取剪贴板/窗口内容 采集范围只由宿主绑定窗口与契约白名单决定，插件不能请求额外字段 部分：uiaView/taskIds 未与数据分级挂钩
插件间越权互访 单插件解析、无跨包引用、冲突即拒 已具备
更新通道供应链投毒 来源与完整性校验 阻断：无签名、无来源校验
权限提升（借宿主特权） 不接回调/句柄/图像 已具备
滥用为跨应用注入通道 输出仅限解释/短问/已观察候选 ID 部分：需输出白名单强校验
插件崩溃致宿主不可用 畸形数据整目录拒绝 已具备

阶段二（公开安装）

威胁 前置条件 现状缺口
窃取窗口内容 安装前权限清单展示 + 运行期强制 缺失：无权限声明模型
插件间越权 显式启用清单、单目标单插件、跨包隔离 部分：catalog.json 有，隔离无
供应链投毒 签名+发布者+可复现构建+灰发 阻断
权限提升 信任等级“已验证/未验证”，装≠进支持范围 阻断：无等级模型
跨应用注入 目标冲突拒绝、不自动扩容支持清单 部分
崩溃致宿主不可用 禁用/移除/回滚 + 变更取消受影响会话 阻断

阶段三（可执行适配器）

威胁 前置条件 现状缺口
窃取剪贴板/窗口内容 OS 强制隔离 + 不传句柄/图像/原文 阻断
插件间越权互访 独立低权限账户 + IPC 白名单 阻断
供应链投毒 签名、可复现构建、吊销、灰发、回滚 阻断
权限提升 Job Object / AppContainer / 受限令牌 阻断
跨应用注入 禁 UI Access、禁跨进程注入、无写入通道 阻断
崩溃致宿主不可用 独立进程 + 看门狗 + 可观察终止 阻断（现有仅对可信代码）

二、阶段二→三门槛（AND，须同时满足）

  1. 已验证通过的操作系统强制隔离：低权限账户/AppContainer + Job Object 限内存·CPU·进程·网络
  2. 不向插件传句柄、图像、控件原文，仅结构化受限 IPC
  3. 能力令牌：按会话最小授权、用户可见可撤
  4. 代码签名 + 发布者身份 + 吊销 + 灰发 + 回滚
  5. 崩溃/超时/超资源可观察终止，不侵占 3s / 90MB
  6. 权限可视化审阅 + 不可篡改审计
  7. 文档写入仍受 TC-3，首轮不开放

任一不满足的降级路径：①停留“数据包 + 审核后并入内置贡献”；②仅独立低权限进程跑只读采集，经白名单 IPC 回传结构化结果，无写入、无 UI 操作。

三、三阶段判定

  • 阶段一：放行，前提为补来源校验与审计日志。
  • 阶段二：有前提放行，四条阻断项清零后方可公开分发。
  • 阶段三：暂缓，AND 门槛未满足前不设计开放路径。

四、应预留但契约中缺失的挂载点

能力令牌；权限沙箱描述符（声明→宿主强制）；信任等级与来源/签名元数据字段；插件权限可视化 UI；行为审计事件流；IPC 契约版本与 kill switch；插件-会话绑定失效通知。

# 走查项 覆盖 缺口描述 不补的返工阶段
1 生命周期 缺失 只定义了 catalog.json 启用清单和「重启生效」，没有安装、禁用、移除、升级、降级流程，也没有残留清理与禁用后会话失效的定义 阶段二强制返工（EXT-03 明列）

3 故障与恢复 部分 有大小、深度、文件数上限和畸形数据拒绝，但存在病态数据导致的计算爆炸（阻塞点规则、UIA 遍历规模）没有上限；宿主崩溃后快照与标记如何复原、启动顺序竞争（采集器先于快照就绪）均未定义 阶段二（故障隔离）/阶段三

7 第一方双标准 部分 系统弹窗 S、WPS 写入 D 需要系统级监听与写回，公开契约无法表达；这些能力只能留在底座，形成「契约内无权限、契约外有特权」的隐性双通道——与 EXT-01「不按应用分支」直接冲突 阶段一埋雷，阶段三引爆
8 并发与冲突 部分 有 plugin_conflict（匹配重叠拒绝），但没有：冲突时用户可选或可视化处置、多会话并存、浮层与全局快捷键归属、多插件标记争用 阶段二（体验）/阶段三（阻塞）

product/product-manager · 19.9s · 19,973 tokens

迁移排序原则

  1. 机制先于知识：无状态、无权限、纯展示的知识先迁，用最小的包建立契约信心。
  2. 特权不下放：需要系统级监听、句柄、写入的能力永久留宿主；契约表达不了就不迁（否则 EXT-01 失效）。
  3. 阻断项清零才进下一批：签名、权限声明、回滚、版本语义四条未清，不启动分发相关批次。
  4. 每批可单开关回滚：以 catalog.json 空清单为总闸，禁止不可逆迁移进入批次。
  5. 契约只在批次边界变更，批内冻结；探针先于迁移。

批次 × 功能 × 前置依赖 × 验证标准 × 返工风险

1 S 类任务无法用「阻塞点+任务 ID」表达 用纯声明式跑通 1 个 S 任务；需新增规则类型即判定契约不足
2 标题漂移/多实例致错绑 同一任务在 20 种窗口标题下重放，统计唯一匹配命中率
3 病态规则 × UIA 规模计算爆炸破 3s 造 5000 节点树 + 200 条规则的包，测单阶段耗时

第一方插件化的隐性成本

  • 双份契约：宿主内部端口契约 + 公开 plugin.json 契约需同步演进，一人+AI 维护成本约翻倍。
  • 特权曝光两难：写进公开契约即向第三方开放，不写则形成「契约外特权通道」，EXT-01 名存实亡。
  • 节奏耦合：schema 冻结后第一方无法随宿主自由改字段；第一方要跟宿主发版，第三方包独立。
  • 审核流程摩擦：自家包也须走签名、灰发、回滚，削弱其交付速度优势。
  • 无测试人力：回归全靠 Checks，插件组合后用例爆炸，覆盖不足即成隐性回归债。

company/chief-technology-officer · 34.7s · 38,656 tokens

1. 结论

有条件可行。 关键条件三个：① 第一方不享受特权，结构定为“机制宿主 + 知识插件”；契约表达不了的能力永久留宿主，不得伪装成插件；② 阶段一只开放声明式数据包，生命周期、权限、版本、分发四个状态机不补齐，绝不进入公开分发；③ 3 秒、90MB、TC-1~6 门禁一分不放宽。

2. 分级建议

A 级（缺任一则结论降为不可行）

  • A1 P0｜生命周期状态机：安装/启用/禁用/移除/残留清理，禁用即取消会话。责任：Plugins 运行时。验证：Checks 用例——禁用后会话立即失效、无残留标记。
  • A2 P0｜第一方特权显式化：S 监听、D 写入定义为宿主受控端口，公开同权或明写“不开放”。责任：架构。验证：探针 5——第三方同权调用一次，无特权泄露。
  • A3 P0｜病态输入上限：阻塞点规则条数、UIA 规模、输出白名单强校验。责任：Plugins。验证：5000 节点树 + 200 条规则单阶段 ≤3s 且可观察结束。
  • A4 P0｜签名、来源校验与更新失败回滚。责任：宿主/分发。验证：篡改包被拒；回滚后空清单零应用。

B 级（P1，显著降风险）

  • B1 P1｜权限声明 + 撤销后降级。责任：Plugins。验证：撤销同意不崩、已加载包即刻收窄。
  • B2 P1｜版本兼容窗口与 version 语义，坏包只拒单包。责任：Plugins。验证：改 schemaVersion/version 造不兼容包，仅该包被拒、其余照常解析，Checks 全绿。
  • B3 P1｜崩溃恢复与启动顺序竞争。责任：宿主。验证：采集器先于快照就绪时重启无标记/快照残留。
  • B4 P1｜冲突的用户可见处置。责任：宿主 UI。验证：造两包匹配同目标，用户可见冲突提示且可择一，选择后单目标单插件生效。

C 级（P2，可选优化）

  • C1 P2｜数据归属与迁移路径。责任：宿主。验证：卸载后无孤儿数据、备份可迁移。
  • C2 P2｜多会话/浮层/快捷键归属。责任：宿主 UI。验证：两会话并存不争用浮层与快捷键。

3. 第三方插件三阶段裁决

  • 数据包：放行。 硬前提：来源校验 + 审计日志 + 输出白名单，且装包≠进已发布支持范围。
  • 公开安装：暂缓。 前提：A1、A4 与权限声明、版本兼容四条阻断清零；未清零只走“审核后并入内置贡献”。
  • 可执行适配器：否决。 重启条件：七项 AND 全绿——OS 强制隔离、不传句柄/图像/原文、可观察终止不侵占 3s/90MB。

4. 决策反转条件（kill criteria）

  1. 探针 2：同一任务在 20 种标题下唯一匹配命中率 <95% 或错绑可复现 → 匹配退回内置清单。
  2. 探针 3：5000 节点 + 200 规则单阶段超 3s，收敛上限也压不下来 → 知识层降为宿主内置贡献。
  3. 一人+AI 维护双份契约，Checks 连续两个批次通过率下滑 → 砍第三方通道，只留第一方声明包。

架构可行性评估报告

一、结论

有条件可行。 一句话理由：知识层为有界纯数据、机制层有明确不可下沉边界，二者可分离；代价是契约必须明确豁免机制层。

关键前提三条：① 第一方不享受特权，结构定为“机制宿主 + 知识插件”；契约表达不了的能力永久留宿主，不得伪装成插件；② 阶段一只开放声明式数据包，生命周期、权限、版本、分发四个状态机不补齐，绝不进入公开分发；③ 3 秒、90MB、TC-1~6 门禁一分不放宽。缺任一，结论降为不可行。

二、架构边界判定

底座不可插件化能力共八项，下沉后的故障均可指认：悬浮窗生命周期/置顶（Z 序乱、TC-6 破）、全局输入监听/注入（可记录全屏按键、跨进程注入）、进程/权限模型（借宿主令牌提权）、配置/密钥存储（密钥入包、跨包互读）、更新分发（绕过签名门禁、半更新契约不兼容）、日志/遥测（直写标题与控件原文）、IPC/宿主 API 网关（自开通道，鉴权与配额失控）、崩溃恢复（会话与标记残留）。

三、声明式插件的表达力上限

七类能力无法声明式表达，降级方案与代价如下：自定义渲染浮层→宿主通用面板/标记（体验中、成本低，仍值）；长驻监听系统事件→触发时一次性采集（体验高损，S 类任务失去触发时机，价值窄）；跨应用注入/自动操作→只指路、用户执行（体验高损，仍值）；本地 DB 事务/跨会话编排→无状态 + 宿主配置（高损、价值窄）；网络长连接/回调→仅宿主模型网关（高损）；动态全局快捷键、自定义采集→固定宿主键 + UIA control/raw + 阻塞点（中损、成本中）；文档写入→宿主受控端口、插件仅知识（体验损低、成本高）。

结论：声明式输出恒为三态——解释、必要短问、指向一个已观察候选 ID。任何依赖状态或时机的任务，由宿主端口承载，不靠扩 schema 补齐。
